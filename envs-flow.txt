flagctl envs 环境发现流程说明
============================

本文说明 `python flagctl.py --db <库文件> envs` 从公开命令行入口到
stdout 名单输出之间的完整路径与每一处分支判定，回答一个具体问题：
为什么 flags 表中明明有某环境的记录，`envs` 的名单里却可能没有它。
本文只描述现有行为，关键结论均注明 flagctl.py 中的现有函数名与分支
条件，可直接与源码核对；不新增命令、不改变任何公开行为，既有源码、
README、SQLite 表结构及其他命令的行为均保持不变。

文中样例结果均为“根据源码推导的预期”，本文不声称样例已经实际执行。

核心区分：**有记录** 与 **有合法直接设置** 不是一回事。flags 表里存
在某环境的行，只说明“有记录”；该环境要出现在 envs 名单中，必须至少
有一行的键是当前合法键、且值是严格文本 `"true"` 或 `"false"`。

一、整体流程概览
----------------

envs 不接收环境名或键名参数（build_parser() 中
`sub.add_parser("envs", ...)` 没有任何位置参数）。main() 的 envs
分支只有一条语句：

    result = json.dumps(cmd_envs(args.db), ensure_ascii=False)

cmd_envs() 内部严格按以下顺序执行，任一环节抛 FlagError 都由 main()
统一处理（退出码 2，stderr 仅输出错误码加换行，stdout 为空）：

  1. 经 open_flag_store() 打开/核对存储状态（与 list/unset/get 共用
     同一份分类规则），在其上下文里执行全表查询
     `SELECT env, key, value FROM flags`；
  2. open_flag_store 给出 VALUE_NOT_SET（库文件缺失但父目录存在、
     有效库缺 flags 表）时，cmd_envs 将其翻译为空名单 []；其余
     STORAGE_ERROR 原样上抛；
  3. 逐行扫描全库所有行：未知键的行整行忽略；合法键的行交给
     stored_bool_text() 做单值校验，校验通过（含 "false"）才把该行
     的环境名原样放入集合；任一合法键的值非法，立即抛
     STORAGE_ERROR，整个调用失败；
  4. 对集合做 sorted() 去重排序，返回名称列表；
  5. main() 用 json.dumps(..., ensure_ascii=False) 序列化为单行
     JSON 数组，成功时由统一出口 `sys.stdout.write(result + "\n")`
     输出，退出码 0。

二、入口与输出协议（main() 的 envs 分支）
------------------------------------------

* envs 子命令没有环境名、键名参数，因此 main() 中既不会执行
  normalize_env()（strip）也不会执行 validate_env()。这两个函数只
  作用于“用户在命令行传入的环境名”；名单中的名称全部来自数据库
  读出的 env 列，从头到尾不经过任何规范化处理（详见第五节）。
* 成功协议：cmd_envs() 返回列表，main() 以
  `json.dumps(cmd_envs(args.db), ensure_ascii=False)` 序列化后
  统一执行 `sys.stdout.write(result + "\n")`，退出码 0，stderr 为
  空。ensure_ascii=False 意味着非 ASCII 名称按原字符输出而非
  `\uXXXX` 转义；默认分隔符下数组元素间是 `", "`（逗号加空格），
  故两元素名单形如 `["Dev", "dev"]`。
* 失败协议：cmd_envs() 抛出的任何 FlagError 都由 main() 末尾的
  `except FlagError as exc: sys.stderr.write(exc.code + "\n");
  return EXIT_ERROR` 统一处理——退出码 2（EXIT_ERROR），stdout 为
  空，stderr 仅为错误码加一行换行。envs 这一条流程只可能抛一种错误
  码：STORAGE_ERROR。名单要么完整输出，要么完全不输出，不存在部分
  名单。

三、存储状态分类（open_flag_store()，只读命令共用的唯一一份）
--------------------------------------------------------------

cmd_envs() 不自行判断存储状态，而是在 open_flag_store() 上下文里
执行查询，源码中的分类分支如下：

1. 库文件路径不存在（`os.path.exists(db_path)` 为假）：
   - 父目录 `os.path.dirname(os.path.abspath(db_path))` 不是目录
     （`os.path.isdir(parent)` 为假）->
     `raise FlagError("STORAGE_ERROR")`；
   - 父目录存在 -> `raise FlagError("VALUE_NOT_SET")`。此分支在
     连接之前就返回，不会创建库文件。
2. 库文件存在：调用 connect()（即 sqlite3.connect），连接本身抛
   sqlite3.Error -> FlagError("STORAGE_ERROR")。
3. 连接成功后，查询在上下文内执行，异常分类为：
   - sqlite3.OperationalError 且信息含 "no such table"（有效库缺
     flags 表）-> FlagError("VALUE_NOT_SET")；
   - 其余 sqlite3.Error（含目标文件不是有效 SQLite 库、flags 表缺
     少 env/key/value 等查询所需列、其他连接或查询失败）->
     FlagError("STORAGE_ERROR")。

cmd_envs() 对这份分类只做一处翻译：

    except FlagError as exc:
        if exc.code == "VALUE_NOT_SET":
            return []
        raise

即“没有数据”的信号在 envs 语义下是空名单而非错误：

* 父目录存在但库文件缺失 -> 输出 []，退出码 0；
* 有效库缺 flags 表 -> 输出 []，退出码 0；
* STORAGE_ERROR（父目录缺失、无效库、所需列缺失、连接或查询失败）
  -> 退出码 2，stdout 为空，stderr 仅 `STORAGE_ERROR` 加换行。

注意 flags 表存在但为空、或表里没有任何合法键记录的情形不属于存储
异常：查询成功返回零行（或没有任何行通过第四、五节的过滤），集合为
空，sorted([]) 得到 []，同样退出码 0。

四、全库扫描与逐行判定（cmd_envs）
----------------------------------

进入扫描的 SQL 没有任何环境过滤：

    rows = conn.execute("SELECT env, key, value FROM flags").fetchall()

随后对全库每一行套用同一个循环：

    for env, key, value in rows:
        if key not in KNOWN_KEYS:   # 当前 KNOWN_KEYS = {"new_ui"}
            continue
        stored_bool_text(value)     # 非法即抛 STORAGE_ERROR
        envs.add(env)

由此得到三类行的确定行为：

1. 未知键的行（key 不在 KNOWN_KEYS，如 "other_key"）：整行忽略，
   循环直接 continue。**忽略包括值本身**——未知键存的是 "yes"、
   "TRUE"、空串或任何异常文本，都不会触发校验，也不影响名单。因此
   只含未知键行的环境不出现，且这不是错误。
2. 合法键、合法值：stored_bool_text() 只接受严格文本 `"true"` 或
   `"false"`（`value == "true" or value == "false"`），不修剪空白、
   不转换大小写，也不接受 "TRUE"、"yes"、"1" 等写法。校验通过后
   原值是 "true" 还是 "false" 都执行 envs.add(env)——**"false" 是
   实际保存的直接设置，与 "true" 一样使环境上榜；false 绝不等于
   未设置**。
3. 合法键、非法值：stored_bool_text() 抛
   FlagError("STORAGE_ERROR")，异常直接穿出 cmd_envs()。此时集合
   里已经收集到哪些环境全部作废，main() 走失败协议，**不输出部分
   名单**。

全库校验范围——不要误用单目标读取的规则：

* get/list 是“单目标”读取：get 的 SQL 带
  `WHERE env = ? AND key = ?`，list 带 `WHERE env = ?`。它们只校验
  目标范围内的合法键值；其他环境的行、以及未知键行的异常值都不在
  读取范围内，不影响结果。
* envs 是“环境发现”，读取范围是**整个 flags 表、所有环境**。库中
  任意环境（哪怕是你不关心的环境、哪怕该环境同时还有另一行合法值）
  的合法键存有 "true"/"false" 之外的值，本次 envs 调用就整体报
  STORAGE_ERROR。单目标命令“别处的损坏与我无关”的规则在此不适用。
* 查询先 fetchall() 取全表、再逐行校验，且 SQL 不带 ORDER BY，行
  的物理返回顺序不由源码保证；但因为每一行都会被检查到，合法键非法
  值无论落在返回顺序的哪个位置，结果必然是 STORAGE_ERROR，与顺序
  无关。去重与排序（sorted）只在整表校验全部通过后才有机会执行。

五、为什么“库里有记录的环境”仍可能不在名单里
----------------------------------------------

综合第三、四节，一个在 flags 表中确有行的环境名，在 stdout 名单中
缺席只有以下几种互斥情形：

1. 该环境的行全部是未知键行：行存在，但每行都在
   `if key not in KNOWN_KEYS: continue` 处被忽略。环境不出现，调用
   仍成功（退出码 0）。
2. 该环境（或库中任意其他环境）存在合法键的非法存储值：这不是
   “悄悄地不列入”，而是整个调用报 STORAGE_ERROR，名单完全不输出。
   不能把这种情况理解为“该环境没设置”。
3. 名称文本与预期不完全相同：名单输出的是库中保存的 env 原文。
   envs 不调用 normalize_env()，不去除两端空白、不折叠大小写：
   `" Dev "`、`"Dev"`、`"dev"` 是三个不同的名称，会分别作为三个
   条目参与排序输出；库里存的是带空白或另一套大小写的名字时，按
   `"Dev"` 的预期去看名单自然“找不到”，但它可能以原样文本在列。

反向澄清：值为严格文本 "false" 的合法键行**一定**使环境上榜，不存
在“false 被当作未设置而缺席”的情况；这与 unset（删除整行）之后的
缺席有本质区别。

六、去重、排序与名称原文输出
----------------------------

* 去重：收集容器是 set（`envs = set()`），同一环境名有多行合法键
  合法值时只输出一次。返回前统一 `sorted(envs)`。
* 排序：sorted() 对 Python str 使用默认序，即逐字符比较 Unicode
  码点。例如空格 U+0020 排在大写字母 U+0041–U+005A 之前，大写字母
  排在小写字母 U+0061–U+007A 之前，`"é"`（U+00E9）排在 ASCII 字母
  之后；故库中名称 `" Dev "`、`"A"`、`"Dev"`、`"dev"`、`"é"` 的
  输出顺序为 `[" Dev ", "A", "Dev", "dev", "é"]`。用户问题中
  `"Dev"` 在 `"dev"` 之前，正是大写 D（U+0044）小于小写 d
  （U+0064）。
* 原文输出：env 列文本从读出到 envs.add 再到 json.dumps 全程原样
  传递，不 strip、不 casefold、不做 NFC/NFKC 之类归一；
  json.dumps 带 ensure_ascii=False，非 ASCII 字符原样出现。仅有的
  字符变换是 JSON 编码本身（若名称含引号、反斜杠等 JSON 特殊字符，
  按 JSON 规则转义）。

七、只读边界
------------

envs 全程只执行一条 SELECT：

* 不创建父目录、不创建数据库文件、不创建 flags 表（建文件/建表的
  SCHEMA 只出现在 set 与非空 import 共用的 save_flags() 写入路径
  上，与本流程无关）；库文件缺失且父目录存在时，open_flag_store()
  在调用 sqlite3.connect 之前就以 VALUE_NOT_SET 返回；
* 不修改、不修复任何记录：stored_bool_text() 只判定单条文本，不做
  查询也不回写；发现非法值的唯一动作是抛 STORAGE_ERROR；
* 失败调用不留下部分输出：错误经 main() 只写 stderr，stdout 为空。

八、固定样例（源码推导的预期）
------------------------------

共同前置状态：当前工作目录（demo.sqlite 的父目录）存在；demo.sqlite
是有效 SQLite 库，含结构如下的 flags 表：

    CREATE TABLE flags (
        env   TEXT NOT NULL,
        key   TEXT NOT NULL,
        value TEXT NOT NULL,
        PRIMARY KEY (env, key)
    )

样例一：合法名单

* flags 表仅含三条记录：
  (env='Dev', key='new_ui', value='true')
  (env='dev', key='new_ui', value='false')
  (env='qa',  key='other_key', value='yes')

调用：

    python flagctl.py --db demo.sqlite envs

预期：

* 退出码 0；stderr 为空；
* stdout 为单行 `["Dev", "dev"]` 加换行。

依据（cmd_envs 逐行分支）：

* Dev/new_ui='true'：键在 KNOWN_KEYS 中，stored_bool_text() 通过，
  envs.add("Dev")；
* dev/new_ui='false'：同一路径，"false" 是严格合法值，照常
  envs.add("dev")——false 不被当作未设置；
* qa/other_key='yes'：键未知，整行 continue，值 "yes" 根本不被校验，
  qa 不入集合，也不构成错误；
* sorted() 按码点排序，"Dev"（D=U+0044）先于 "dev"（d=U+0064）；
  json.dumps 默认分隔符给出 `["Dev", "dev"]`，main() 追加换行，
  退出码 0。

样例二：任一合法键非法值 -> 全库失败

把样例一中 dev 一行的值改为 'TRUE'（大写），其余两行不变：
  (env='Dev', key='new_ui', value='true')
  (env='dev', key='new_ui', value='TRUE')
  (env='qa',  key='other_key', value='yes')

调用同上。预期：

* 退出码 2；stdout 为空；
* stderr 仅为单行 `STORAGE_ERROR` 加换行。

依据：扫描到 dev/new_ui 时键合法，stored_bool_text("TRUE") 因不做
大小写转换而失败，抛 FlagError("STORAGE_ERROR")，异常穿出
cmd_envs()。Dev 虽有完全合法的记录也不能挽救输出——envs 的校验范围
是全库，任一行合法键非法值即整体失败，已收集的集合作废，不输出
["Dev"] 这样的部分名单；qa 的未知键行依旧被忽略，与本次失败无关。

边界情形（同一命令，失败统一沿用第二节的错误输出协议：退出码 2、
stdout 空、stderr 仅 `STORAGE_ERROR\n`；空名单统一为 stdout `[]\n`、
退出码 0、stderr 空）：

* 父目录存在但 demo.sqlite 文件缺失：open_flag_store() 取
  VALUE_NOT_SET 分支，cmd_envs() 翻译为 [] -> 输出 []，退出 0；
* demo.sqlite 是有效库但缺少 flags 表：查询抛含 "no such table" 的
  OperationalError，归类 VALUE_NOT_SET -> 输出 []，退出 0；
* flags 表存在但为空，或全表只有未知键记录（如只有
  qa/other_key='yes'）：查询成功、扫描后集合为空 -> 输出 []，
  退出 0；
* 库文件的父目录缺失：open_flag_store() 中 isdir(parent) 为假 ->
  STORAGE_ERROR；
* 目标文件存在但不是有效 SQLite 数据库（如内容是普通文本）：
  connect() 或查询抛 sqlite3.Error -> STORAGE_ERROR；
* flags 表缺少查询所需列（如表只有 env、key 两列，SELECT env,
  key, value 无法执行）：OperationalError 信息不含 "no such
  table"，走“其余 sqlite3.Error”分支 -> STORAGE_ERROR；
* 其他连接或查询失败：同样由 open_flag_store() 归为 STORAGE_ERROR。

以上每种情形都只做读取探测：不创建目录、文件或表，也不修复记录。

九、情形汇总
------------

成功（退出码 0，stderr 空，stdout 为单行 JSON 数组加换行）：

  1. 库中至少一个环境有合法键的严格 "true"/"false" 记录（"false"
     也算）：输出去重、按码点升序后的环境原名数组；
  2. 父目录存在但库文件缺失：[]；
  3. 有效库缺 flags 表：[]；
  4. flags 表为空，或全表没有任何合法键记录（含只有未知键行）：[]。

失败（退出码 2，stdout 空，stderr 仅 `STORAGE_ERROR\n`）：

  1. 库父目录缺失；
  2. 目标文件不是有效 SQLite 数据库，或连接失败；
  3. flags 表缺少查询所需列（env/key/value），或查询失败；
  4. 全库任意一行的合法键保存了 "true"/"false" 之外的值（全库校验
     范围，不输出部分名单）。

未知键行（无论其值是什么）在任何情形下都被整行忽略，既不产生环境
条目，也不产生错误。

十、源码依据索引
----------------

* build_parser()：`sub.add_parser("envs")` 不注册任何环境名/键名
  参数——envs 无输入名需要规范化。
* main() 的 `if args.command == "envs"` 分支：
  `json.dumps(cmd_envs(args.db), ensure_ascii=False)`；成功统一经
  `sys.stdout.write(result + "\n")` 输出并以 0 退出；
  `except FlagError` 统一为 stderr 错误码加换行、退出码 2。
* cmd_envs()：open_flag_store() 上下文中执行
  `SELECT env, key, value FROM flags`（全库、无环境过滤）；
  VALUE_NOT_SET 翻译为 []，其余异常上抛；逐行
  `if key not in KNOWN_KEYS: continue`、stored_bool_text(value)
  校验、envs.add(env)；最后 sorted(envs) 去重排序。
* open_flag_store()：os.path.exists + os.path.isdir(parent) 区分
  父目录缺失（STORAGE_ERROR）与文件缺失（VALUE_NOT_SET）；connect()
  失败 -> STORAGE_ERROR；上下文中含 "no such table" 的
  OperationalError -> VALUE_NOT_SET，其余 sqlite3.Error ->
  STORAGE_ERROR。
* stored_bool_text()：已保存布尔值的唯一读取校验，仅接受严格文本
  "true"/"false"，否则 STORAGE_ERROR；不修剪、不转换大小写、不查询、
  不修复。
* KNOWN_KEYS：`frozenset({"new_ui"})`，当前唯一合法键，决定“未知
  键整行忽略”与“全库校验”的键范围。
* 对照（不属于本流程，仅用于区分范围）：cmd_get()/read_flag_with_source()
  的 `WHERE env = ? AND key = ?`、cmd_list() 的 `WHERE env = ?`
  是单目标读取；cmd_envs() 的无 WHERE 全表扫描是环境发现，二者的
  校验范围不可混用。
